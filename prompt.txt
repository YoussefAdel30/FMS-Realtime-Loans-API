# 1. Project Overview

The API receives an MSISDN and determines whether the MSISDN is eligible to perform an operation.

Eligibility is determined using a large daily CSV blacklist.

The CSV contains up to **10 million MSISDNs**, with multiple dynamically configurable blacklist sources.

Expected production traffic is **500 requests per second**.

The application must be optimized for:

- High throughput.
- Low response latency.
- Efficient memory utilization.
- Thread safety.
- Zero-downtime blacklist replacement.
- Reliable asynchronous auditing.
- Direct Oracle database integration.
- Automatic CSV audit exports.
- Recovery after application or server failures.
- Simple RHEL deployment and maintenance.

The application must be configurable through an external `application.yml` located alongside the JAR.

The system must be maintainable by an operations engineer without modifying Java source code.

# 4. API Requirements

Implement:

```http
POST /api/v1/eligibility/check
Content-Type: application/json
```

Request:

```json
{
  "msisdn": "201066257228"
}
```

Blacklisted response:

```json
{
  "requestId": "unique-request-id",
  "msisdn": "201066257228",
  "result": "KO",
  "reasons": [
    "Anti-Fraud (Vishing)",
    "Anti-Fraud (Financial Fraud)"
  ],
  "blacklistVersion": "20261015"
}
```

Eligible response:

```json
{
  "requestId": "unique-request-id",
  "msisdn": "201055555555",
  "result": "OK",
  "reasons": [],
  "blacklistVersion": "20261015"
}
```

Business rules:

- MSISDN not found: `OK`.
- MSISDN found with one or more active flags: `KO`.
- MSISDN found with all-zero flags: `OK`.
- Return every active source as a rejection reason.
- HTTP 200 for valid eligibility decisions.
- HTTP 400 for malformed requests.
- HTTP 503 when the application is not ready or cannot safely accept audit events.
- HTTP 500 for unexpected failures.

Generate a unique request ID for each request.

Use the same ID for response tracing, application diagnostics, Oracle records, and CSV auditing.

Preserve MSISDN as a string in all external interfaces.

Make MSISDN validation rules configurable.

Default to 12-digit Egyptian MSISDNs starting with `20`.

# 5. Blacklist CSV Format

Example:

```csv
MSISDN,Vishing,Suspicious_IMEI,Financial_Fraud
201066257228,1,0,1
201012345678,0,1,1
201098765432,1,0,0
```

The number of source columns is dynamic.

The application must read source names from the CSV header.

Use configurable human-readable source names:

```yaml
sources:
  display-names:
    Vishing: "Anti-Fraud (Vishing)"
    Suspicious_IMEI: "Anti-Fraud (Suspicious IMEI)"
    Financial_Fraud: "Anti-Fraud (Financial Fraud)"
```

Support up to 64 sources using a Java `long` bitmask.

Handle all 64 bits correctly, including the sign bit.

If more than 64 sources are encountered, reject the file with a clear validation error.

Support configurable duplicate handling, initially merging flags using bitwise OR.

Reject invalid MSISDNs, invalid flags, malformed CSV structures, and conflicting headers according to the configured validation policy.

# 6. High-Performance Blacklist Engine

Use:

```java
Long2LongOpenHashMap
```

The key represents the numeric MSISDN.

The value represents the source bitmask.

Do not create a separate Java object for every MSISDN.

Do not store the entire CSV as a collection of strings.

Optimize parsing and memory allocation.

The blacklist must support approximately 10 million records.

Use a configurable initial capacity and load factor.

Implement an immutable snapshot wrapper containing:

- Lookup map.
- Source definitions.
- Source display names.
- Snapshot version.
- Load timestamp.
- Record count.
- Source count.
- Source-file metadata.

Use:

```java
AtomicReference<BlacklistSnapshot>
```

Every request must read the active snapshot once.

Never mutate a published snapshot.

Concurrent lookups must not require global synchronization.

# 7. Daily Blacklist Reload

Implement a background loader that:

1. Scans a configurable input directory.
2. Detects new blacklist CSV files.
3. Waits until a file has been completely published.
4. Supports `.ready` marker files.
5. Validates the CSV.
6. Builds a completely new primitive map.
7. Validates the resulting snapshot.
8. Atomically activates the new snapshot.
9. Retains the previous valid snapshot.
10. Records reload metrics and operational logs.

Never clear the active blacklist before the new one is ready.

Never expose a partially loaded blacklist.

If the new CSV fails validation, continue using the previous valid snapshot, subject to the configured freshness policy.

Support startup recovery from the last successfully validated blacklist.

Do not report API readiness until a valid blacklist is available.

Make the maximum permitted blacklist age configurable.

Ensure older blacklist files cannot overwrite newer versions.

Provide manual reload verification instructions in `docs.md`.

# 9. Asynchronous Audit Logging

The API must not synchronously insert audit records into Oracle.

Implement a bounded asynchronous audit pipeline.

Initial settings:

```yaml
audit:
  async:
    enabled: true
    queue-size: 65536
    worker-count: 1
    overflow-policy: block-with-timeout
    overflow-timeout-ms: 10
```

Audit records must contain:

- Request ID.
- Request timestamp.
- Response timestamp.
- MSISDN.
- Eligibility result.
- Reason mask.
- Human-readable reasons.
- Blacklist version.
- HTTP status.
- Processing time.
- API instance.

Use structured JSON Lines.

Example:

```json
{"requestId":"req-001","msisdn":"201066257228","result":"KO","reasonMask":"5","reasons":["Anti-Fraud (Vishing)","Anti-Fraud (Financial Fraud)"],"blacklistVersion":"20261015"}
```

Separate audit files from general application logs.

Use a bounded queue.

If the queue is full, wait for the configured timeout.

If the event cannot be accepted, return HTTP 503 rather than silently dropping it.

We explicitly accept the small crash-related loss window associated with asynchronous logging.

Do not claim guaranteed durability for records that remain in memory or unflushed operating-system buffers.
